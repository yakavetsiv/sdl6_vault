## Session — 22:36 UOroboros image-processing pipeline architecture

## Summary
Cloned and analyzed `spgarcica/uostore` and `AC-SDL6/image_analysis_uos` to evaluate whether UOroboros fits complex image-processing pipelines. The framework is a good conceptual fit for typed, auditable, reusable image workflows, but the current image-analysis UO package needs compatibility fixes before registration and execution.

## Files Created / Modified
- [[GitHub/uostore]] — framework overview, architecture, strengths, and current role.
- [[GitHub/image_analysis_uos]] — image UO package overview, intended operations, and compatibility issues.
- [[UOroboros Image Pipeline Design Notes]] — manifest, audit, retention, dimensionality, database, and distributed-execution decisions.
- `/Users/iyakavets/Documents/Github/Uoroboros/uostore` — cloned framework repo.
- `/Users/iyakavets/Documents/Github/Uoroboros/image_analysis_uos` — cloned image-analysis UO repo.

## Key Decisions
- Use UOroboros as the orchestration and provenance layer, not as the heavy image data transport layer.
- Pass manifest paths and metadata between UOs; keep image arrays on disk or object storage.
- Keep the original metadata CSV immutable. Use JSON run manifests plus per-stage CSV snapshots for derived state.
- Each UO should emit a stage manifest and `audit.json` containing parameters, code version, timing, checksums, inputs, outputs, warnings, and per-file status.
- A 7-day retention policy is appropriate for recomputable intermediate images if manifests, audit records, code commits, environment locks, and raw/source data are retained.
- Dimensionality-reducing steps such as stitching and merging are acceptable if the manifest supports many-to-one lineage through `derived_from`, `axes`, `shape`, `kind`, `channel`, and `channels`.
- Multi-machine execution is plausible through a distributed backend such as Prefect, with shared storage and a shared UOroboros database.

## Technical Findings
- `image_analysis_uos` currently fails to import against the cloned `uostore`: `@uoroboros_type(condition=..., code=..., message=...)` is not supported by the current framework decorator.
- The current `uostore` API expects routing metadata on `@unit_operation(outputs={...})` using `OutputCondition`, not on Pydantic type decorators.
- The image-analysis flow JSON uses `context.*` mappings; local UOroboros execution appears to map from `input` and `result`, so parameter passing likely needs redesign.
